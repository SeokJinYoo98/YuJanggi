# 1. 프로젝트 개요

가족과 장기를 두며 보다 체계적으로 승리하기 위해 시작한 프로젝트입니다.

단순한 로컬 플레이 구현이 아닌,
장기 규칙을 **구조적으로 모델링**하고
AI 및 네트워크 대전까지 확장 가능한 **구조 설계**를 목표로 개발했습니다.

> 입력 / 로직 / 표현을 분리하여
**확장 가능한 턴제 게임 구조**를 설계하는 것을 목표로 했습니다.
> 

---

# 2. 핵심 설계 목표

이 프로젝트에서 가장 중요하게 고려한 점은
**게임 로직을 Unity로부터 분리하는 것**이었습니다.

이를 통해 동일한 로직을
다양한 실행 환경에서 재사용할 수 있는 구조를 목표로 설계했습니다.

- Local 대전
- AI 대전
- Network 대전

---

# 3. 설계 핵심

### 3-1. Core와 Runtime의 분리

게임 로직을 Core영역에 분리하고,
Unity는 View와 Input 처리만 담당하도록 구성했습니다.

이를 통해 게임 규칙과 상태 변화가
**엔진 구현에 종속되지 않도록 설계**했습니다.

### 3-2. Live와 Replay의 분리 ⭐

리플레이 기능은 단순히 **과거 기록을 재생하는 기능이 아니라,
현재 진행 중인 라이브 게임과 독립적으로 동작**해야 한다는 전제로 설계했습니다.

이를 위해 Live 상태와 Replay 상태를 분리하고,
GameSession이 현재 SessionState에 따라 
입력 처리와 화면 갱신 흐름을 제어하도록 구성했습니다.

### 3-3. Rule 분리

이동 가능 수 계산은 크게 다음 단계로 분리했습니다.

1. 후보 수 생성
2. 왕궁 룰 적용
3. 장군 여부 기반 합법 수 필터링

이를 통해 장기 규칙을
단순 조건문 나열이 아닌 **규칙 처리 흐름으로 구조화**했습니다.

### 3-4 입력과 로직 분리

입력 처리와 게임 로직의 결합을 피하기 위해
Controller 계층을 두고,
최종 Select / Move 요청만 GameSession에 전달하도록 구성했습니다.

GameSession은 State에 따라
입력 처리와 화면 갱신 흐름을 제어하도록 설계했습니다.

이를 통해 **로컬 입력 / AI 판단 / 네트워크 입력**을 
**동일한 흐름으로 처리** 할 수 있는 구조를 구축하였습니다.

### 3-5. 이벤트 기반 구조

게임 상태 변화는 이벤트를 통해 외부에 전달하고,
GameSession은 이를 수신해 MatchView에 화면 갱신을 요청합니다.

이를 통해 MatchModel이 UI와 View를 직접 참조하지 않도록 구성했습니다.

# 4. 해결한 문제

## 4-1. 리플레이 기능 추가 과정에서 발생한 Live / Replay 흐름 충돌 문제

### 🚨 **[문제]**

리플레이 모드를 처음 구현할 때는 Live용 Presenter와 Replay용 Presenter를 분리해 처리했습니다.

하지만 두 Presenter가 같은 화면 요소를 제어하면서,
현재 상태가 Live인지 Replay인지에 따라 “if” 분기가 늘어났고,
이벤트 호출 순서가 꼬이면서 **중복 호출이 발생했고,**
판단하는 로직의 증가로 **코드가 복잡해졌습니다.**

> 기능은 분리했지만, **화면 흐름을 제어하는 기준이 명확하지 않아**
오히려 유지보수 및 확장이 어려운 구조가 되었습니다.
> 

### 👾 [고민]

문제의 핵심은 Presenter의 개수가 아니라,
”현재 입력과 화면 갱신을 어떤 흐름으로 처리할 것인가”를 **판단하는 주체가 없다는 점**이라고 판단했습니다.

단순히 기능을 나누는 것만으로는 충분하지 않았고,
각 기능이 실행되어야 하는 **상태와 호출 순서**를 명확히 제어할 필요가 있다고 생각했습니다.

### 👍 **[해결 방안]**

이를 해결하기 위해 **Session 흐름에 State 패턴**을 도입했습니다.

LiveState와 ReplayState를 분리하여
각 상태가 처리할 수 있는 입력과 화면 갱신만 담당하도록 리팩토링했습니다.

또한 **공통 흐름은 SessionStateBase에 통합하고**,
Enter / Exit 및 요청 처리 순서를 디버그 로그로 추적하면서
중복 호출과 호출 순서 문제를 확인하고 수정했습니다.

이후 동일한 구조를 기반으로 
**EndState, EndReplayState도 간단한 코드 추가만으로 확장**할 수 있었습니다.

### 📋 **[결과]**
리플레이 모드 도입 과정에서 발생했던
**중복 호출, 순서 꼬임, if 분기 증가 문제를 줄일 수 있었습니다.**

또한 상태별 책임이 명확해지면서,
현재 게임이 Live인지 Replay인지에 따라
**입력 처리와 화면 갱신 흐름을 안정적으로 분리할 수 있었습니다.**

> 이를 통해 **Live와 Replay의 실행 흐름을 보다 안정적으로 관리**할 수 있었습니다.
>

## 4-2. 이동과 합법성 검증 분리

### 🚨 **[문제]**

이동 후보 생성과 합법성 검증을 하나의 로직에서 처리하면서
하나의 구조가 여러 책임을 동시에 가지게 되었고,
규칙이 추가될수록 복잡도가 증가하는 문제가 발생했습니다.

> 이동 후보 생성과 합법성 검증이 하나의 로직에 섞이며
**규칙이 추가될수록 코드가 복잡해지고 중복이 증가**하는 문제가 발생했습니다.
> 

### 👍 **[해결]**

이를 해결하기 위해 규칙 계산 과정을 다음과 같이 분리했습니다.

1. **MovementRule: 이동 패턴 기반 후보 생성**
- 대부분의 말 → Pattern Movement
- 車 / 包         → Directional Movement
    
    > “먼저 이동 가능한 **후보 칸**”만 계산
    > 
1. **PalaceRule: 왕궁 규칙 별도 적용**
- 士 / 宮   → 왕궁 내부 제한
- 卒·兵      → 왕궁 전진 방향 대각 이동
- 車 / 包   →  왕궁 대각 슬라이딩
    
    > **위치 기반 규칙**은 별도로 처리
    > 
1. **JaggiRule: 합법 수 필터링**

합법 수 판단을 위해 다음 구조를 도입했습니다.

- DoMove            → 표현과 분리된 채 데이터에서만 이동
- IsKingInCheck → 장군 여부검사
- UnDoMove      → 상태 복구
    
    > **장군이 되는 경우** → 불법 수로 필터링
    > 

### 📋 **[결과]**

> **이동 후보 생성과 합법성 검증을 분리함으로써
규칙 추가 시 코드 중복을 줄이고 구조를 단순화할 수 있었습니다.**
> 

또한 다음과 같은 확장이 가능해졌습니다.

- 합법성 검사를 제외한 **자유 이동 모드**
- **AI 탐색**에서 동일한 구조 재사용
- 리플레이 및 상태 검증로직 결합 용이
    
    ---
    

## 4-3. 입력 해석과 게임 로직 분리

### 🚨 **[문제]**

초기 설계에서는 MatchManager가 입력 처리와 Selection 상태를 동시에 관리하였고,
이로 인해 입력 계층과 게임 로직 계층이 결합되면서 책임 분리가 이루어지지 않았고,
특히 AI 도입의 경우 같은 명령이지만 진입점이 달라지는 문제가 발생했습니다.

> **로컬 입력에 의존적인 구조로 인해 AI 및 네트워크 환경에서 로직 재사용이 불가능했고,
확장성이 크게 제한되었습니다.**
> 

### 👍 **[해결]**

1. **PlayerController 기반 입력 해석**
- Local / AI / Network Controller 각각 입력을 독립적으로 처리 해석
- 입력 결과를 (From, To) 형태의 Move 요청으로 변환
    
    > **입력은 Controller**에서 해석하고, **MatchManager는 요청만 처리**
    > 
1. **MatchManager 책임 축소**
- Selection 상태 및 입력 해석 로직 제거
- 순수 게임 상태 관리 및 규칙 검증만 담당
    
    > 입력 로직과 무관한 **순수 로직 계층**으로 분리
    > 
1. **Rule 기반 합법 수 검증 유지**
- Controller는 Rule을 통해 이동 가능 여부만 조회
- 실제 상태 변경은 MatchManager에서만 수행
    
    > 상태 변경 책임을 **단일 계층으로 제한**
    > 

각 Controller는 동일한 PlayerController 인터페이스를 따르되, 
입력 해석 방식에 따라 역할을 분리했습니다.

- **AI**
    - Rule을 기반으로 합법 수를 탐색하고, 선택된 Move를 MatchManager에 전달
- **Local**
    - 보드 프레젠터 및 입력 이벤트를 통해 사용자 입력 해석,
    - 말(인덱스)과 이동 가능 위치를 시각적으로 표현 요청을 전달 한 뒤 Move 요청 전달
    - BoardPresenter → 선택 말, 불법 합법 수 하이라이트

### 📋 **[결과]**

입력 해석과 게임 로직을 분리함으로써
입력 방식에 영향을 받지 않는 구조를 구축하게 되었습니다.

이로 인해 다음과 같은 확장이 가능해졌습니다.

- AI Controller를 통한 자동 플레이 구현
- Network 환경에서도 동일한 Move 데이터 기반 동기화 가능
- **입력 방식 변경에도 게임 로직 수정 없이 재사용 가능**
    
    > **모든 입력은 PlayerController 에서 해석되지만, 
    시스템 내부에서는 동일한 Move 요청 형태로 통합됩니다.**
    >

# 💡5. 인사이트

턴제 구조에서 입력 / 로직 / 표현을 분리한 경험을 통해,
실행 환경에 따라 책임을 분리하는 구조의 중요성을 배웠습니다.

이 경험을 기반으로,
향후 Server / Client 구조로 확장 가능한 방향을 고민하고 있습니다.

---

# ⭐ 6. 향후 개선 계획

### 1. 네트워크 기반 멀티 플레이 확장

- 로컬 및 AI 대전 구조를 기반으로,
Core 로직을 서버에서 실행하는 멀티플레이 구조로 확장할 계획입니다.
- 우분투 기반 서버 환경을 구축하고,
Client-Server 구조에서 게임 상태 동기화를 검증할 예정입니다.

### 2. AI 고도화

- 현재의 단순 합법 수 탐색 및 랜덤 선택에서 나아가
MinMax, Alpha-Beta Pruning 기반의 의사결정 구조를 도입할 계획입니다.
- 전략적으로 대응하는 AI 구현할 에정입니다.

### 3. 모바일 확장

- UI를 모바일 환경에 맞게 재구성하고,
플랫폼 확장을 통해 멀티 디바이스 환경에서 플레이 가능하도록 개선할 예정입니다.
